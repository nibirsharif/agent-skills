# Changelog

Versions follow `.claude-plugin/plugin.json`. Claude Code uses that version to decide when installed users get an update, so every release bumps it.

## 0.20.0

Two changes to write-spec's replies: a draft for each statement that waits on a question ([#21](https://github.com/nibirsharif/agent-skills/issues/21)), and questions about facts in a named system's code ([#22](https://github.com/nibirsharif/agent-skills/issues/22)), the finding of the first real run that was still open for it ([evals/real-runs/2026-11-17.md](evals/real-runs/2026-11-17.md)). Every count below was run on `claude-sonnet-5-5` (Claude Code 2.1.327).

- write-spec: a statement that lacks only a system name or a value is also shown as a `Draft:` line below the questions ([#21](https://github.com/nibirsharif/agent-skills/issues/21)): the EARS sentence it will become, with `[Q-NNN]`, the question that fills it, in place of each missing part. A draft is not a requirement: it has no ID and is never saved to a requirements file. It holds only the input's words and its slots, changes no requirement and no question, and is not written for a coverage gap, an impression, or a statement that does not say what the system does. Before, 4 or 5 of the benchmark's 10 first replies wrote no requirement, only questions; now 0 or 1 shows neither a requirement nor a draft, the one being a one-line idea nothing can be written from. No requirement or draft holds an invented value, and the open decisions found are 39 to 41 of 49 against a mean of 41.3 without drafts, inside the benchmark's no-change margin of three: [after-drafts.md](evals/write-spec/benchmark/after-drafts.md). The rules are in a new reference, `drafts.md`, which the workflow opens only after the requirements and questions are linted, and a second lint follows. Read up front, the same rules made every reply ask fewer questions.
- write-spec: when the input or an answer names a system, it lists the project's top-level folders, and when one holds that system's code it reads at most 5 of its files and may ask about a fact there that would change a requirement ([#22](https://github.com/nibirsharif/agent-skills/issues/22)): something a statement relies on that the code lacks, a rule the code enforces that the input does not mention and that stops a response, or a value the input says is today's where the code has another. The question states the fact and names its file, and carries no `Proposed:`. No requirement is written from the code. In the real run write-spec raised none of the design facts the code held, because its rules forbade any question that came from the project. The rules are in a new reference, `code-facts.md`, read only when a folder holds the named system's code. New cases `code-facts` and `code-no-facts`: 6 of 6 at 3 runs each.
- write-spec's lint checks `Draft:` lines as requirements. It fails a draft with no slot, a slot whose question the reply does not ask, a requirement that holds a slot, a draft above a question, and a draft in a saved file.
- write-spec's word budget went from 4,700 to 5,330, and a run reads 5,327 words, from 4,633. `drafts.md` is counted because every reply reads it; `code-facts.md` is not. A reply costs about $0.16 on the benchmark, against $0.14, for the second file and the second lint.
- Evals: write-spec has 13 cases, from 10. The suite passed 37 of 39 at 3 runs with the judge; the misses are `nfr-ids`, once, which asked a fourth question, and the new case `draft-slots`, once, on an input since reworded. After the last two wording fixes to `drafts.md`, the six cases a draft can appear in passed 18 of 18, and the whole suite was not run again. `propose-system` and `vague-only` check drafts too, and four golden replies show them.
- Not measured: the follow-up turn with drafts, whether a draft whose slots are answered comes back as a requirement marked `(new)`; a reply that saves a file after showing drafts; and for the code questions, the limit of 5 files, a large project, and the real run's project.
- One new reply line, `Draft:`, which a script that reads write-spec's replies must expect after the question lines. No file format, ID, stop line, or config key changes: a saved `requirements.md` is the same as before. [#23](https://github.com/nibirsharif/agent-skills/issues/23) and [#42](https://github.com/nibirsharif/agent-skills/issues/42) stay open.

## 0.19.0

Fewer, larger phases from write-plan ([#10](https://github.com/nibirsharif/agent-skills/issues/10)), and implement-task runs the project's lint, format, and type checks ([#9](https://github.com/nibirsharif/agent-skills/issues/9)). These were the last two findings of the first real run ([evals/real-runs/2026-11-17.md](evals/real-runs/2026-11-17.md)). Every count below was run on `claude-sonnet-5-5` (Claude Code 2.1.327).

- implement-task: it runs the project's check commands before it edits anything and again once the test suite is green, and commits only when all pass ([#9](https://github.com/nibirsharif/agent-skills/issues/9)). The commands are the list in the new config key `check_commands`; when the key is empty, the lint, format-check, and type-check commands the project's CI config runs; with no CI config, none. `none` turns the checks off. It never runs a CI step that builds, installs, publishes, or deploys. It fixes a failing check only inside the task's Files, and a formatter runs on those files by path. A check that already fails before the task starts, or one the task cannot fix in its own files, is the existing failed-check stop line; a check whose tool is not installed is the existing missing-service line. The Done report's Check line names each check after the tests. In the real run a build task committed a test file that failed `ruff format --check`, which the project's CI runs. New cases `check-commands`, `ci-checks`, and `check-fails`: 9 of 9 at 3 runs each, and the suite 18 of 18 at one run each. Its word budget went from 3,350 to 3,480 for the new rule.
- write-plan: it cuts the fewest phases that fit its two limits ([#10](https://github.com/nibirsharif/agent-skills/issues/10)). A feature that fits both limits is one phase however many flows it has, only what is over a limit is cut, a file counts once for a phase however many of its requirements touch it, and neighbours that fit the limits together are merged. With no code for the feature, each Size is a guess and the requirement limit alone sizes the phases; before, each small phase got its own guess of 3 to 9 files, and any two neighbours then passed the limit of 10. A requirement that applies to what several phases build goes in the first of them. The defaults stay 8 requirements and 10 files a phase, so 29 requirements are still at least 4 phases: for a spec of many small requirements, raise `plan_max_requirements_per_phase` together with `tasks_max_per_phase`. A `plan.md` that exists keeps its phases. The benchmark's five plans have 9 phases against 20, all in the reference ranges (2 of 5 before), and every before and together item holds (17 of 17, against 15 of 17): [baseline-0.19.0.md](evals/write-plan/benchmark/baseline-0.19.0.md). The suite passed 29 of 30 at 3 runs with the judge, as before; the miss is a sentence before the location question. A run reads 3,100 words, from 3,072, inside the unchanged budget.
- write-tasks: the default `tasks_max_per_phase` is 16, from 12. A phase that write-plan fills to 8 requirements needs 9 to 12 tasks, and write-tasks refused one with `Phase 1 needs more than 12 tasks.` in 1 of 3 runs; at 16, 3 of 3 runs wrote 10, 9, and 9 tasks. A task is the same size as before: one behaviour. Set `tasks_max_per_phase: 12` to keep the old limit. The suite passed 10 of 10 at one run each.
- Evals: write-plan's `multi-phase` and `phase-dependency` cases bound the number of phases (3 or 4, and 2 or 3) and no longer check a size against the file limit, since they have no codebase. Its benchmark has three new dev inputs: `dev-note-tags` and `dev-note-tags-small-limit` run in a project with code and show the file limit cutting and a file counted once, and `dev-saved-searches` has a scope that names more than its requirements state, which the plans leave out in 3 of 3 runs. write-spec's benchmark reference for `hold-workspaces` agrees with the skill's expiry example, and its three records are scored again ([#27](https://github.com/nibirsharif/agent-skills/issues/27)).
- README: a section on how much of the chain to run for each size of change, and the eval table's note that its runs are three per case.
- Not measured: write-plan on a feature of many files in a large project. The two benchmark inputs with code are one small project, and the real run was not repeated.
- No file format, ID, reply line, or stop line changes. One new config key, `check_commands`, and one changed default, `tasks_max_per_phase`. [#21](https://github.com/nibirsharif/agent-skills/issues/21) to [#23](https://github.com/nibirsharif/agent-skills/issues/23) stay open.

## 0.17.0

Fixes for the remaining bugs from the first real run ([evals/real-runs/2026-11-17.md](evals/real-runs/2026-11-17.md)), [#3](https://github.com/nibirsharif/agent-skills/issues/3) to [#8](https://github.com/nibirsharif/agent-skills/issues/8). Each case below was run on `claude-sonnet-5-5` (Claude Code 2.1.327).

- build-phase: a verify-spec report must have exactly one row for each ID of the requirements file, in file order ([#3](https://github.com/nibirsharif/agent-skills/issues/3)). `parse_reply.py verify` takes `--requirements <path>`, and build-phase passes it on every verify parse. A report that leaves an ID out, repeats one, or names an unknown one is invalid, and keeps its rows for the gap-carry rule. In the real run a retry listed only the phase's four rows, leaving out the 25 skipped ones, and was accepted.
- implement-task: after the task's commit, each untracked file the run's commands created is removed by path with `git clean -fd -- <path>` ([#4](https://github.com/nibirsharif/agent-skills/issues/4)). `.agent-skills-config.yaml` and the task's own Files are never removed, `git clean` never runs without a path, and a stop removes nothing. In the real run `uv run pytest` left a `uv.lock` behind that stopped the next task. New case `test-leftover`: 3 of 3.
- implement-task: before editing any file it runs the test command once, and when the tests cannot run because a service or tool outside the project is not available, it stops with a new line ([#5](https://github.com/nibirsharif/agent-skills/issues/5)): `<id> cannot run its tests: <what> is not available (<command>: <error>). Make it available, then run implement-task again.` It never starts, installs, or configures a service, container, or tool, never points the tests elsewhere, and never skips them. `parse_reply.py` knows the line, so build-phase relays it with build-phase as the command to rerun. In the real run one subagent started a database container itself and the next stopped with `check failed`. New case `service-missing`: 3 of 3.
- Chain: write-plan, write-tasks, implement-task, verify-spec, and build-phase find a feature's files by one rule, worded the same in each ([#6](https://github.com/nibirsharif/agent-skills/issues/6)). Without `spec_output_dir`, a path to the feature's requirements.md, plan.md, or tasks.md from earlier in the conversation gives its folder; otherwise they ask, and never search the project or pick a path. The lookup scripts ask `Where is <file>? Give its path, or set spec_output_dir in .agent-skills-config.yaml.`, which build-phase replies with in place of a summary and verify-spec's contract now allows. write-plan and write-tasks ask `Where is <file>? Give its path, set spec_output_dir in .agent-skills-config.yaml, or paste the <requirements|plan>.`, save beside any file they read, and end a reply left in chat because its input was pasted with `Not saved: the <requirements|plan> was pasted, not read from a file. Name a folder to save <plan.md|tasks.md> in.`, unless the user asked for chat only. New cases: write-plan `ask-location` and `pasted-not-saved`, write-tasks `pasted-not-saved`, build-phase `no-spec-dir`. The four affected suites passed 41 of 41 at one run each.
- implement-task, verify-spec: without `base_branch`, the default branch is the one `origin/HEAD` names, else `main`, else `master` ([#7](https://github.com/nibirsharif/agent-skills/issues/7)). Before, a stale local `main` came first. implement-task never uses a local `main` or `master` that is not the default branch as a base and never deletes it. New case `origin-head`: 3 of 3, against 1 of 3 with 0.16.0's wording.
- write-tasks: every item under a phase's Interface and data changes is built by a task of that phase, whether or not a Verify line names it ([#8](https://github.com/nibirsharif/agent-skills/issues/8)). That task names the item and tests it, and later tasks that use the item depend on that task instead of building it again. An item the code already has gets no task, and the Overview names its file. An item that no ID of the phase needs is a question. New case `interface-item`: 3 of 3 with the judge. It also passed with the old wording, so it guards the rule but does not reproduce the real run's miss, which came from a longer, five-phase plan.
- `tests/test_shared_blocks.py` checks that the rules shared between skills (finding the files, the default branch) are worded the same in each.
- No file format or ID changes. New reply lines: implement-task's stop for tests that cannot run, the location questions, and the `Not saved` line of write-plan and write-tasks. `parse_reply.py verify` has a new option. Every bug found in the real run is now fixed; [#9](https://github.com/nibirsharif/agent-skills/issues/9) and [#10](https://github.com/nibirsharif/agent-skills/issues/10) stay open as enhancements.

## 0.16.0

- build-phase: a gap verify-spec found is no longer lost when its report is rejected and the retry says `met` ([#2](https://github.com/nibirsharif/agent-skills/issues/2)). A `Tally:` line that miscounts the rows no longer rejects a report: the rows decide, and `parse_reply.py` returns the tally counted from them (still a failure with `--strict`, which the evals use). A report rejected for another reason keeps its rows in the script's output, and when the retry gives one of its gap rows a verdict that is not a gap, the run stops with `Stopped: verify-spec gave <ID> <first verdict> in a rejected report and <second verdict> on the retry. ...` instead of trusting either report.
- build-phase: subagent replies reach `parse_reply.py` through a file in the system temp directory, written whole, never retyped into a heredoc. In a real run the retyped report had lost 24 rows.
- `Verify:` in the summary is the tally counted from the last report's rows.
- Evals: `bad-verify-report`'s test double is now invalid for a `met` row with no evidence, since a miscounted Tally no longer is. New case `miscounted-tally`: a report whose Tally miscounts its rows is used, not retried, and the summary has the tally counted from the rows.
- build-phase: a new script, `scripts/summary.py`, prints the summary from the run's values (feature, phase, branch, counts, the `Verify:` value, any `Check by hand:` checks, and the stop reason or phase title). Every run that `find_tasks.py` does not stop ends with it, and the reply is its output copied whole. Since 0.15.0 made `parse_reply.py` mandatory, a stop the agent decided from the script's JSON was written out as a sentence before the summary: `round-limit` passed 0 of 3, against 3 of 3 before. Wording alone brought it to 2 of 3; with the script, the whole suite passed 36 of 36 at 3 runs on `claude-sonnet-5-5` (Claude Code 2.1.327), and 39 of 39 with the #2 fix above. The reply lines are unchanged, and where the agent cannot run commands it writes the same lines itself.
- No file format or ID changes. One new reply line: build-phase's stop when a retried verify-spec report no longer calls a gap of its rejected first report a gap. Known issues [#3](https://github.com/nibirsharif/agent-skills/issues/3) to [#10](https://github.com/nibirsharif/agent-skills/issues/10) from 0.15.0 are still open.

## 0.15.0

- implement-task: a new script, `scripts/pick_task.py`, does the first three workflow steps: it finds `tasks.md`, checks the working tree, and picks the task. It prints `found <path>` and `task <T-id>` (with ` rework` for a task that already has a commit), or `stop <the stop line>`, or `ask <what>`. It decides these stop lines: no tasks file, uncommitted changes, no Status lines, no such task, already Done, a dependency not Done, a requirement no task covers, and every task Done. Task mismatch, a failed check, and a rework with nothing to fix are still the agent's. The five stop-line eval cases passed 30 of 30 with it, against about half before, when most misses were a sentence before a correct stop line.
- implement-task: asked for a requirement in place of a task (`--requirement FR-003`), the script takes the first task not yet `Done` that builds it, never the phase's verify task. Before, the rules did not say which task that was.
- verify-spec: a new script, `scripts/check_scope.py`, does the first two workflow steps: it finds `requirements.md` and checks the named ID or phase. It prints `found <path>` and `scope <all, an ID, or a phase with its IDs>`, or `stop <the stop line>`, or `ask <what>`. Every stop line of the skill now comes from it. `unknown-id` and `missing-requirements` passed 12 of 12.
- Evals: benchmarks for verify-spec, write-plan, and write-tasks, in the format of write-spec's: inputs with hidden references, a `dev-*` and a `hold-*` set, scored by hand, each with a baseline on `claude-sonnet-5-5`. verify-spec got every verdict right on six projects with planted faults (36 of 36 rows, no gap called `met`). write-plan covered every ID and kept every dependency, and cut more and smaller phases than the references in 3 of 5 plans. write-tasks covered every ID with checks that can be run; 4 of 44 tasks hold two changes. `evals/bench.py` now runs an input in a copy of its `project/` folder and records the model ID.
- write-plan: a new stop line. When one requirement alone needs more files than `plan_max_files_per_phase`, the reply is exactly `<ID> needs more than <n> files on its own. Split it with write-spec, then run write-plan again.` and no plan is written. Before, the skill spread such a requirement over several phases and wrote phases that listed no requirement ID (3 of 3 eval runs); with the rule the case passed 4 of 4. A new reply line, so the next release is a MINOR one.
- Evals: two more write-plan cases, `phase-dependency` (phases follow what each step needs, not the order of the IDs) and `oversized-requirement` (the stop above).
- Evals: a case or benchmark input can have a `branch/` folder, committed on the branch `feature-work`, so drift on a feature branch can be tested.
- build-phase: a new stop reason. In an agent that cannot start subagents, the run stops after picking the phase with `Stopped: This agent cannot start subagents, which build-phase needs. Run implement-task for each task of phase <n>, then verify-spec, yourself.` and changes nothing. Before, the rules forbade doing the work in its own context and did not say what to do instead. The docs page answers the question in its FAQ.
- Evals: seven more build-phase cases, so every stop reason has one: `round-limit`, `subagent-stop-line`, `malformed-reply-twice` (a test-double `implement-task` skill in the case's project), `gap-no-task`, `no-subagents`, `all-done`, and `off-phase-branch`. The last two passed 2 of 3: a sentence before the summary, and a wrong verify-spec Tally that build-phase copied without running `parse_reply.py`. The whole suite at 3 runs on `claude-sonnet-5-5`: 26 of 27, the miss a sentence before a correct `gap-no-task` summary. `rework-recovers`'s `Tasks:` check is now exact: 2 of its 3 runs counted the verify task as implemented, which the rules forbid, The reply contract and build-rules.md now say that `<k>` is the build tasks implemented for the first time and `<r>` the ones reopened, and that the verify task is in neither, with a wrong-and-right example; `rework-recovers` then passed 3 of 3. No reply format change.
- build-phase: `build_max_rework_rounds` now takes effect. `scripts/find_tasks.py` prints it as `rounds <n>` on the line after `found <path>` (2 when it is not set), and the rules say to stop when the rounds made equal it, at once for 0. Before, the first `round-limit` run never read the config file and reworked past a limit of 0. A value that is not a whole number is a question. The three lookup scripts' shared core changed to carry this; implement-task's and verify-spec's print what they did before.
- build-phase: `scripts/find_tasks.py` prints the every-task-Done stop as the whole stopped summary when no phase is named, as it does for a missing `tasks.md`. It takes `--phase <n>` for a named phase, which it leaves to the rules. `all-done` passed 3 of 3, against 2 of 3 before.
- build-phase: every subagent reply goes through `parse_reply.py`, done ones too, and the run acts on its verdict. Before, the step was skipped in every run checked, and a verify-spec report whose Tally did not match its rows was copied into the summary. An invalid verify report twice now ends the run with `Verify: no usable report` and `Stopped: verify-spec gave no usable reply twice`, a new reply value and stop. New case `bad-verify-report` (a test-double verify-spec): 3 of 3.
- Evals: a case can name `"disallowed_tools"` in its `checks.json`, tools the agent is denied in that case.
- Evals: `.gitignore` hid the `.agent-skills-config.yaml` in a case's `committed/` folder, so the implement-task `test-command` case's config was never in the repository and the case ran without it on a fresh clone. It is tracked now.
- Evals: [evals/real-runs/2026-11-17.md](evals/real-runs/2026-11-17.md) records the whole chain run once on a real, private project (`claude-sonnet-5-5`, Claude Code 2.1.327): where it stopped or needed a person, and twelve findings. Three are fixed below; the rest are listed there as open.
- build-phase: an implement-task stop line is passed on with build-phase as the command to rerun. Before, a build-phase summary could end `..., then run implement-task again.`, which sends the user to the wrong skill. `parse_reply.py` gives the line to copy as `relay`. `subagent-stop-line` now expects `... then run build-phase again.` A changed reply line.

- build-phase: `Tasks:` counts only this run's tasks, never those of an earlier run in the same conversation. In the real run a rerun reported `Tasks: 1 implemented` after implementing none.
- No file format or ID changes. New reply lines: write-plan's stop, build-phase's no-subagents and verify-twice stops, `Verify: no usable report`, and build-phase's relayed stop lines. Where the agent cannot run commands, each skill's written rules still apply.

## 0.7.0

- New skill `verify-spec`: checks the code against a saved `requirements.md` and replies with one table: a verdict per `FR` and `NFR` (`met`, `partial`, `unmet`, `untested`, `cannot tell`, `skipped`) with `file:line` and test evidence, then `Tests:`, `Tally:`, and `Drift:` lines. `met` needs the code and a test that ran and passed in this run, and the weaker verdict wins when two fit. Can be limited to one phase of `plan.md` or one ID, or run on pasted requirements. Blocked requirements are `skipped`, and `tasks.md` is never read. Read-only: runs the project's test command once, edits nothing, commits nothing. A missing requirements file, an unknown ID or phase stops with one line.
- Evals: `evals/verify-spec/` has a fixture with planted gaps (a missing implementation, a missing test, a vague NFR, a blocked requirement, an uncommitted stray file) and nine cases; `hooks.py` checks the reply's shape, the tally against the rows, and the evidence a `met` row needs.
- Known: in eval runs (Sonnet, 27 runs) about 85% passed. About one reply in ten opens with a sentence before the table or the stop line, and the drift line is occasionally wrong when the only changed file is an uncommitted one.

## 0.6.0

- New skill `implement-task`: implements one task from a saved `tasks.md`, the named `T-` ID or the next `Todo` task whose dependencies are `Done`. Changes only the task's files, adds the test its Done when names, runs the full suite, sets the task's Status to `Done`, and commits it on the feature branch (created from the default branch when needed), staging by path. Never pushes. On its first run it first commits the feature's own spec files (requirements, plan, tasks) as `Add <feature-name> spec`, so the chain can run straight after write-tasks. A missing tasks file, an unfinished dependency, blocked work, a task that does not fit the code, changes outside the feature's folder, or a failing check stops with one line.
- write-tasks: every task has a sixth part, `**Status:** Todo` or `Done`. A phase with a `Done` task counts as started when `tasks.md` is updated, so write-tasks no longer has to ask. Files saved by 0.5.0 have no Status lines; re-run write-tasks to add them.
- Evals: a skill's `config.json` can name a `"fixture"` folder that every case starts in, committed as a git repository on `main`; a case's `dirty/` folder is copied over it uncommitted.
