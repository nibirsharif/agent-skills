# Real run, 27 November 2026

The chain of 0.21.0 run on a real project's whole product document, and its output compared with the requirements, plan, and task list the same project already had from an early version of the skills. write-spec, write-plan, and write-tasks were the subject; build-phase ran on two phases at the end. The project is private, so it is described only as far as the findings need. It is the project of [the first real run](2026-11-17.md).

## The run

- **Project:** a private Python web backend (uv, pytest, Ruff, pyright, Alembic migrations, PostgreSQL), three phases of it built and merged. Its CI runs lint, format, type, and import-boundary checks besides the tests.
- **Input:** the project's product requirements document, about 8,200 words with 62 numbered requirement rows, each with a priority and a release phase. Its architecture document, about 18,300 words, was given as the answer to write-spec's first questions.
- **The existing files:** a `requirements.md` of 244 requirements after five revisions, a `plan.md` of 55 phases, and a `tasks.md` of 323 tasks, written on 26 and 27 October 2026 with the skills as they were between 0.8.0 and 0.9.0, from the same two documents. What the person typed at each turn then is not recorded.
- **When and with what:** 27 November 2026, `claude-sonnet-5-5`, Claude Code 2.1.327, the skills of 0.21.0 loaded with `claude --plugin-dir`. Every step ran once, with `claude -p`, and write-spec's later turns with `--resume`. No person typed anything: an agent started each step and answered write-spec's questions from the decisions the existing `requirements.md` records, leaving eight questions open.
- **Where:** spec, plan, and tasks ran in a copy of the project that held only its documents, with `spec_output_dir: docs`, which is the state the existing files were written in. build-phase ran in a clone of the project at its default branch, with the remote removed and its own database.
- **Runs:** three write-spec turns, then write-plan and write-tasks on the result (the chain); write-plan on the existing `requirements.md`; write-tasks on the existing `plan.md` and on the new plan; build-phase three times. Eleven runs cost $9.91. Three of them were then repeated on `claude-opus-5-5`, for $11.79.

- The 99 against 244 is not a comparison: the new run stopped after three turns, and the existing file had two more rounds of answers and one of gaps the person found.
- Both plans on the existing requirements cover all 244 IDs once. 31 is the fewest phases the limit of 8 allows.
- On the existing plan, 28 phases have fewer build tasks than before, 21 the same, and 6 more. 28 of the 230 build tasks cover more than one ID, where 1 of 268 did, and they account for 29 of the 38 fewer build tasks; the other 9 are set-up tasks that no longer stand alone.
- The chain's plan covers all 99 written requirements, has two blocked entries for requirements that wait on an open question and are not written yet, and lists all 14 questions with the phase each touches. Its task list covers the 99.

## The same three steps on Opus

Three of the runs again on `claude-opus-5-5` at high effort (`--effort high`), each a new session in a new copy with the input the Sonnet run had: write-spec's first reply from the product document, write-plan on the existing 244 requirements, and write-tasks on the existing 55-phase plan. One run each. They ask which of the findings below come from the model.

| Step | `claude-sonnet-5-5` | `claude-opus-5-5`, high effort |
|------|---------------------|--------------------------------|
| write-spec, first reply | 38 requirements, 15 questions, 1 draft | 35 requirements, 116 questions, 19 drafts |
| Document rows with no requirement and no question | 30 of 62, 10 of the highest priority | 11 of 62, 2 of the highest priority |
| write-plan on 244 requirements | 31 phases, 27 of exactly 8 | 33 phases, 25 of exactly 8 |

| write-tasks on the 55-phase plan | 285 tasks, 230 build tasks | 332 tasks, 277 build tasks |
| Build tasks that cover more than one ID | 28 | 66 |
| IDs named by more than one build task | 13 | 89 |
| Cost of the three runs | $2.29 | $11.79 |
| Time of each run | 2 to 6 minutes | 11 to 20 minutes |

- **write-spec:** Opus asks where Sonnet skips. It asked which system acts for each group of rows that names none, with a draft for each, and wrote no requirement for them; Sonnet named a system the document uses and wrote the requirement. 116 open questions are twelve replies of ten for the person.
- **write-plan:** Opus read the architecture document's build order, wrote the file without a generator script, and every Verify line names what to test. Finding B did not occur. It still fills most phases to the limit, so finding C holds in part.
- **write-tasks:** Opus's phase 4 has four build tasks, one of them the migration with the database role, so finding D did not occur, and its reply is the contract's lines only, so neither did finding F. But it wrote more build tasks than the existing list has (277 against 268): it gives a port, a migration, or a table a task of its own and names the same ID in each, so the rule of one task for an event's requirements made the list no smaller.
- Text between tool calls appeared in all three Opus runs.

The rule is that every gap becomes a question. The existing file shows the same thing happened in October: its last revision added 17 requirements for first-release gaps the person had found, and it still leaves 13 rows out, 2 of the highest priority. | Bug | Open: [#48](https://github.com/nibirsharif/agent-skills/issues/48). |

The existing plan's lines name what to observe, such as the request that is rejected. On the chain's 99 requirements no script was used and none of the 99 lines is a copy. | Quality | Open: [#49](https://github.com/nibirsharif/agent-skills/issues/49). |

One phase's title joins four unrelated subjects, and a phase that builds a gate comes 19 phases before the one that builds what the gate checks. 31 of the existing plan's 55 phases are split across two or more of the new ones. Observations that are not failures:

- The installed plugin on the machine was 0.11.0. A run that does not pass `--plugin-dir` tests that version, not the repository's.
- The first joined task built without trouble: three requirements, one migration and one test file, a check for each ID. This is the build from a joined task that [0.21.0](../../CHANGELOG.md) lists as not measured, measured once.
- write-spec's first reply asked 15 questions where the October reply asked 33, for 38 requirements against 33. With finding A, fewer questions is not better here: the October reply asked about 22 rows it wrote no requirement for, and this one about 3.
- Every proposal write-spec made came from the input: a retention period the document calls a hypothesis, and an event the architecture document names.
- Text between tool calls appeared in 6 of the 8 spec, plan, and tasks runs, and write-spec left its draft reply as a file in the project root in 3 of 3 turns. Both follow from the headless permission rules of these runs, which refused a long heredoc and a command joined with `cd`; neither is counted as a finding.
- A reply of 53 new and 27 changed requirements was linted and saved in one turn of under five minutes. The largest task list took under six.
